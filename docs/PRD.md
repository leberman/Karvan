# PRD: Karvan (کاروان)

کار با Claude Code رو روی هر کدوم از کامپیوترهاتون، دقیقاً از همون جایی که ول کردید، ادامه بدید.

- وضعیت: پیش‌نویس ۴، ۱۴۰۵/۰۸/۲۵ (2026-11-16)
- مسئول: نگهدارنده‌ی پروژه
- زبان برنامه: Go (تصمیم شورای مشاوران، بخش ۱۷)
- مجوز انتشار: MIT یا Apache-2.0، به انتخاب استفاده‌کننده
- اولین انتشار عمومی: فقط لینوکس؛ بعد ویندوز، بعد مک

> Karvan فایل‌هایی را می‌خواند و می‌نویسد که Claude Code و
> اپلیکیشن دسکتاپ Claude روی دیسک نگه می‌دارند؛ ساختار بعضی از آن‌ها مستند نیست و ممکن است عوض شود.

## ۱. مسئله

خیلی‌ها با Claude Code روی بیش از یک کامپیوتر کار می‌کنند (محل کار و خانه، دسکتاپ و لپ‌تاپ). هر چیزی که یک
گفتگو را مفید می‌کند، روی همان سیستمی می‌ماند که گفتگو در آن انجام شده:

- تاریخچه‌ی گفتگوهای Claude Code (ترمینال و بخش Code اپلیکیشن دسکتاپ)؛
- فهرست گفتگوها در اپلیکیشن دسکتاپ؛
- دستورالعمل‌های شخصی (`CLAUDE.md`)، مهارت‌ها (skills) و حافظه‌ی هر پروژه؛
- کار نیمه‌تمام در خود پروژه: شاخه، commitهایی که هنوز push نشده‌اند، تغییرات staged و unstaged.

رفتن به سیستم دیگر یعنی شروع از صفر: نه تاریخچه‌ای برای ادامه، نه حافظه‌ای، و کدی نیمه‌کاره روی سیستمی که الان
خاموش است.

یک نمونه‌ی شخصی (حدود ۶۰۰ خط bash و یک repo خصوصی git) در آبان ۱۴۰۵ یک هفته بین دو سیستم Ubuntu کار کرد و
ایده را ثابت کرد. Karvan آن را به ابزاری تبدیل می‌کند که هر کسی بتواند نصبش کند.

## ۲. کاربران

| کاربر | از چه استفاده می‌کند | چه لازم دارد |
| ---- | ---- | ----- |
| برنامه‌نویس با دو سیستم یا بیشتر | Claude Code در ترمینال و/یا بخش Code اپلیکیشن | تاریخچه، حافظه، مهارت‌ها و کار نیمه‌تمام git روی همه‌ی سیستم‌ها |
| غیربرنامه‌نویس | بخش Code اپلیکیشن دسکتاپ (و Cowork که خودش ابری است) | تاریخچه و فهرست گفتگوها روی همه‌ی سیستم‌ها، بدون ترمینال، git، GitHub یا کلید SSH |

نسخه‌ی ۱ (لینوکس) برای برنامه‌نویس‌هاست. راه غیربرنامه‌نویس‌ها با محل ذخیره‌ی «پوشه‌ی ابری» باز می‌شود (بخش ۷)
که به git و SSH نیاز ندارد؛ این برای ویندوز و مک مهم است.

## ۳. اهداف و غیراهداف

### اهداف

1. گفتگویی که روی یک سیستم شروع شده، روی سیستم دیگر قابل ادامه باشد: هم در ترمینال (`claude --resume`)
   و هم در فهرست بخش Code اپلیکیشن.
2. `CLAUDE.md`، مهارت‌ها و حافظه‌ی پروژه‌ها روی همه‌ی سیستم‌ها یکی باشد.
3. برای برنامه‌نویس‌ها (اختیاری): کار نیمه‌تمام پروژه منتقل شود و با یک فرمان برگردد.
4. حریم خصوصی به‌صورت پیش‌فرض: داده قبل از خروج از سیستم رمزنگاری شود؛ رمزها و توکن‌ها قبل از ارسال
   شناسایی شوند.
5. هیچ چیزی بی‌صدا از دست نرود: نه بازنویسی داده‌ی جدیدتر، نه حذف خطی از گفتگو؛ در تداخل هر دو طرف می‌مانند.
6. بعد از راه‌اندازی، خودکار کار کند: با hookهای Claude Code، یک زمان‌بند، و موقع خاموش شدن.

### غیراهداف (نسخه‌ی ۱)

- همکاری هم‌زمان یا همگام‌سازی بین افراد مختلف.
- پشتیبانی از ابزارهای دیگر (Codex، Cursor، Gemini CLI و...). طراحی جلویش را نمی‌گیرد، ولی در نسخه‌ی ۱ نیست.
- همگام‌سازی اطلاعات ورود، فایل‌های `.env` یا وضعیت ورود به حساب Claude.
- همگام‌سازی گفتگوهای claude.ai یا Cowork (از قبل در فضای ابری ذخیره می‌شوند).
- نسخه‌ی ویندوز و مک (کد نسخه‌ی ۱ باید قابل انتقال بماند؛ بخش ۱۱).

## ۴. چه چیزهایی منتقل می‌شود

| مورد | محل روی لینوکس | پیش‌فرض | توضیح |
| ---- | --------------- | ------- | ----- |
| دستورالعمل‌های کلی | `~/.claude/CLAUDE.md` | روشن | |
| مهارت‌ها | `~/.claude/skills/<name>/` | روشن | به‌جز `skills/synced/` (اپلیکیشن خودش آن‌ها را همگام می‌کند) |
| حافظه‌ی پروژه | `~/.claude/projects/<dashed path>/memory/` | روشن | برای هر پروژه جدا؛ بخش ۵ |
| متن گفتگوها | `~/.claude/projects/<dashed path>/<id>.jsonl` | روشن | N روز اخیر؛ قابل تنظیم، پیش‌فرض ۷ |
| فهرست گفتگوهای اپلیکیشن | `~/.config/Claude/claude-code-sessions/<account>/<org>/local_<id>.json` | روشن | مسیرها برای هر سیستم بازنویسی می‌شوند؛ اپلیکیشن فقط موقع باز شدن می‌خواندش |
| کار نیمه‌تمام پروژه | repoی git خود پروژه | خاموش | برای برنامه‌نویس‌ها؛ شاخه، commitهای push‌نشده، staged، unstaged و فایل‌های untracked (غیر ignored) |
| پوشه‌های شخصی | هر پوشه‌ای که کاربر انتخاب کند | خاموش | مثلاً یادداشت‌هایی که بیرون از پروژه نگه داشته می‌شوند |
| `settings.json` | `~/.claude/settings.json` | هرگز | مخصوص هر سیستم است؛ Karvan فقط hookهای خودش را به آن اضافه می‌کند |
| دستورالعمل‌های مخصوص یک سیستم | `~/.claude/CLAUDE.machine.md` | هرگز | بخش ۴-۱ |

### ۴-۱. تنظیمات مخصوص هر سیستم

پیش‌فرض: همه‌چیز بین سیستم‌ها مشترک است. برای تفاوت‌ها دو راه ساده هست، بدون منطق ادغام:

- **دستورالعمل مخصوص یک سیستم:** `karvan init` در انتهای `CLAUDE.md` مشترک یک خط import می‌گذارد
  (`@~/.claude/CLAUDE.machine.md`) و این فایل را روی هر سیستم می‌سازد. Claude Code خودش آن را می‌خواند، اما
  Karvan هرگز منتقلش نمی‌کند. مثلاً سر کار: «به سرور staging دسترسی داری»؛ در خانه: «VPN خاموش است».
- **حذف برای یک سیستم:** هر سیستم می‌تواند بگوید یک مهارت یا یک پروژه را نمی‌خواهد
  (`karvan exclude skill <name>`). آن مورد روی بقیه‌ی سیستم‌ها دست‌نخورده می‌ماند.

## ۵. پروژه‌ها روی سیستم‌های مختلف

یک پروژه روی سیستم‌های مختلف در مسیرهای مختلف است (`~/work/app` سر کار، `~/temp/app` در خانه). Claude Code
پوشه‌ی هر پروژه را از روی مسیر کامل آن نام‌گذاری می‌کند و اپلیکیشن دسکتاپ هم مسیر کامل را در فایل هر گفتگو
ذخیره می‌کند.

- هر پروژه با آدرس remote ی git آن (به شکل یکسان‌شده) شناخته می‌شود، یا اگر remote ندارد، با اسمی که کاربر
  می‌دهد.
- هر سیستم نقشه‌ی خودش را دارد: شناسه‌ی پروژه ← مسیر محلی.
- در داده‌ی ذخیره‌شده، به‌جای مسیر پروژه یک نشانگر (placeholder) می‌آید؛ هر سیستم موقع بارگذاری مسیر خودش را
  جایگزین می‌کند. فقط ابتدای کامل مسیر جایگزین می‌شود (`/a/app` با `/a/app/x` جور است، با `/a/app-old` نه).
- روی ویندوز، بازنویسی مسیر باید حرف درایو، `\` و بزرگ و کوچک نبودن حروف را درست انجام دهد؛ اسم پوشه‌ی پروژه
  در Claude Code هم با قاعده‌ی همان سیستم ساخته می‌شود.
- پروژه‌ای که روی یک سیستم تعریف نشده، منتقل می‌شود ولی آن‌جا بارگذاری نمی‌شود؛ `status` آن را نشان می‌دهد.

## ۶. موتور همگام‌سازی

درس اصلی هفته‌ی آزمایشی و شورای مشاوران: ادغام git مناسب این داده نیست. فایل‌ها قبل از ارسال رمزنگاری
می‌شوند و git نمی‌تواند فایل رمزنگاری‌شده را مقایسه یا ادغام کند؛ ادغام git همان چیزی بود که نمونه‌ی bash را
هر روز متوقف می‌کرد. پس Karvan موتور همگام‌سازی خودش را دارد و محل ذخیره فقط انبار است.

مشخصات کامل در `docs/sync-engine.md` نوشته می‌شود (فاز ۰). اصول آن:

### ۶-۱. ساختار

- **فایل‌های داده (blob):** هر نسخه‌ی هر فایل، فشرده و (از M1) رمزنگاری‌شده، با اسمی برابر اثر انگشت محتوایش
  (hash) ذخیره می‌شود. محتوای یکسان یک بار ذخیره می‌شود.
- **فهرست هر سیستم (manifest):** هر سیستم فهرست خودش را می‌نویسد: برای هر مسیر منطقی (مثلاً
  `project:<id>/transcripts/<session>.jsonl`)، hash نسخه‌ی فعلی، hash نسخه‌ی پایه (آخرین نسخه‌ای که از بقیه
  دیده)، زمان و حجم. هر سیستم فقط فهرست خودش را می‌نویسد، پس نوشتن دو سیستم با هم تداخل ندارد.
- **ادغام:** هر سیستم فهرست‌های بقیه را می‌خواند، برای هر مسیر با قانون‌های بخش ۶-۲ تصمیم می‌گیرد، نتیجه را روی
  دیسک خودش می‌نویسد و فهرستش را به‌روز می‌کند.
- **پاک‌سازی:** blobهایی که هیچ فهرستی به آن‌ها اشاره نمی‌کند و از بازه‌ی نگهداری گذشته‌اند، حذف می‌شوند.

### ۶-۲. قانون‌های ادغام

| داده | قانون |
| ---- | ---- |
| متن گفتگو | **ترکیب خطوط:** هر خط یک پیام با شناسه‌ی یکتا (`uuid`) است. خطوط هر دو طرف با هم ترکیب و تکراری‌ها حذف می‌شوند و ترتیب از روی زنجیره‌ی پیام‌ها (`parentUuid`) و زمان حفظ می‌شود. هیچ خطی دور ریخته نمی‌شود. اگر یک گفتگو روی دو سیستم شاخه‌شاخه شده باشد، هر دو شاخه در فایل می‌ماند. |
| فایل گفتگو در اپلیکیشن | `lastActivityAt` جدیدتر برنده است. |
| وضعیت خود هر سیستم (عکس فوری کار نیمه‌تمام، فهرست نگه‌داشته‌ها) | هر سیستم مالک مال خودش است؛ هرگز ادغام نمی‌شود. |
| متن (`CLAUDE.md`، حافظه، مهارت‌ها، پوشه‌های شخصی) | اگر فقط یک طرف از نسخه‌ی پایه تغییر کرده، همان برنده است. اگر هر دو تغییر کرده‌اند، ادغام سه‌طرفه‌ی متنی؛ اگر نشد، هر دو نسخه کنار هم نگه داشته می‌شوند (`<name>.conflict-<machine>`)، به کاربر خبر داده می‌شود و بقیه‌ی فایل‌ها متوقف نمی‌شوند. |
| حذف در برابر تغییر | تغییر برنده است. |

### ۶-۳. فایل‌هایی که در حال نوشته شدن‌اند

Claude Code و اپلیکیشن دسکتاپ همزمان با همگام‌سازی این فایل‌ها را می‌نویسند.

- **خواندن:** از هر فایل یک کپی گرفته می‌شود و فقط اگر حجم و زمانش در طول کپی عوض نشده باشد، استفاده می‌شود؛
  وگرنه دور بعد. خط آخر گفتگو اگر به `\n` ختم نشده (نیمه‌کاره)، کنار گذاشته می‌شود.
- **نوشتن:** همیشه در فایل موقت و بعد جایگزینی اتمی (rename).
- **گفتگویی که الان باز است:** گفتگویی که در ۱۵ دقیقه‌ی اخیر نوشته شده، در اجرای زمان‌بند فرستاده نمی‌شود
  (hookها و اجرای موقع خاموشی همه را می‌فرستند). روی سیستم مقصد، فایل گفتگویی که الان باز است بازنویسی نمی‌شود؛
  ادغام برای دور بعد می‌ماند.
- **اپلیکیشن دسکتاپ:** فایل گفتگوی جدید هر وقت نوشته می‌شود. فایل گفتگویی که از قبل هست، فقط وقتی اپلیکیشن
  بسته است عوض می‌شود، چون اپلیکیشن باز ممکن است نسخه‌ی خودش را رویش بنویسد. وقتی اپلیکیشن باز است و چیز
  جدیدی رسیده، به کاربر گفته می‌شود: «اپلیکیشن را با Ctrl+Q ببندید و دوباره باز کنید».
- **قفل:** هر بار فقط یک اجرای Karvan روی هر سیستم.

### ۶-۴. چه زمانی

- hook ی `SessionStart` در Claude Code: گرفتن و بارگذاری.
- hook ی `SessionEnd`: ذخیره و ارسال.
- زمان‌بند، هر ۱۰ دقیقه (قابل تنظیم) تا وقتی سیستم روشن است.
- موقع خروج از حساب و خاموش شدن: ذخیره‌ی همه‌چیز و ارسال.
- دستی: `karvan sync`.

خروجی `SessionStart` به Claude نشان داده می‌شود، پس اجرای عادی چیزی چاپ نمی‌کند؛ اجرایی که به کاربر نیاز
دارد، یک خط ساده چاپ می‌کند.

### ۶-۵. کار نیمه‌تمام پروژه (اختیاری)

برگرفته از `wip.sh` ی نمونه:

- ذخیره: شاخه، HEAD، یک bundle از commitهایی که هیچ remote ی ندارد، diffهای staged و unstaged، و فایل‌های
  untracked که git نادیده نمی‌گیرد (حداکثر ۲۰ مگابایت). درخت بدون تغییر چیزی اضافه نمی‌کند. merge یا rebase در
  جریان قابل انتقال نیست؛ این را بگوید.
- وضعیت هنگام شروع: «کار نیمه‌تمام از <سیستم> (<زمان>، شاخه‌ی <b>) منتظر است» — فقط وقتی واقعاً چیزی نیمه‌تمام
  باشد.
- بازگردانی (فقط با موافقت کاربر): شاخه را بگیرد (اگر HEAD هنوز نبود، همه‌چیز را بگیرد)، به آن برود،
  fast-forward کند و تغییرات را دوباره اعمال کند. به‌جای بازنویسی تغییرات محلی‌ای که هیچ عکس فوری‌ای ندارند،
  امتناع کند. وقتی منتظر شبکه است، بگوید دارد چه می‌کند.
- هرگز در پروژه‌ی کاربر commit، push، stash یا reset نکند.
- این بخش از فرمان `git` خود سیستم استفاده می‌کند؛ کسی که آن را روشن می‌کند، git را از قبل دارد.

## ۷. محل ذخیره

محل ذخیره فقط چهار کار انجام می‌دهد: نوشتن، خواندن، فهرست کردن، و نوشتن شرطی (فقط اگر کسی وسطش عوضش نکرده
باشد). هر چیزی که این‌ها را دارد، می‌تواند محل ذخیره باشد.

| گزینه | برای | زمان |
| ---- | ---- | ---- |
| پوشه‌ی محلی | تست، و هر پوشه‌ای که یک فضای ابری همگامش می‌کند (Google Drive، Dropbox، OneDrive، Syncthing) | M0 (برای تست)، عمومی قبل از ویندوز |
| repoی خصوصی git (GitHub، GitLab، هر remote ی SSH/HTTPS) | برنامه‌نویس‌ها | M0 |
| S3 / R2 / WebDAV | بعداً | — |

الزامات محل ذخیره‌ی git:

- **کاربر چیزی نصب نمی‌کند:** git داخل خود برنامه است (کتابخانه‌ی go-git). Karvan از git فقط به‌عنوان انبار
  استفاده می‌کند: fetch، commit و push ی fast-forward. اگر push به خاطر نوشتن سیستم دیگر رد شد، دوباره fetch،
  ادغام فهرست‌ها و push. هرگز force push نمی‌کند و هرگز به ادغام git تکیه نمی‌کند.
- برای هر ارتباط شبکه‌ای مهلت زمانی و پیام واضح («ارسال نشد، دوباره امتحان می‌شود»).
- بعضی شبکه‌ها SSH روی پورت ۲۲ را متوقف می‌کنند. ارسال گیرکرده را تشخیص دهد و SSH ی GitHub روی پورت ۴۴۳
  (`ssh://git@ssh.github.com:443/...`) را پیشنهاد کند. اختیاری، هرگز پیش‌فرض.
- repoی عمومی را رد کند (در صورت امکان از راه API میزبان بررسی کند)، مگر اینکه کاربر صریحاً بخواهد.
- چون تاریخچه‌ی git همه‌چیز را نگه می‌دارد، اگر رمزی از جست‌وجو جا ماند و فرستاده شد، پاک کردنش یک روال
  دستی و آگاهانه دارد که مستند می‌شود.

## ۸. امنیت و حریم خصوصی

متن گفتگوها شامل کد، محتوای فایل‌ها، خروجی دستورها و گاهی رمز و توکن است.

- **رمزنگاری به‌صورت پیش‌فرض روشن (از M1).** هر blob قبل از رسیدن به محل ذخیره با age رمزنگاری می‌شود. طرح کلید:
  - اولین `karvan init` یک **کلید اصلی** تصادفی (X25519 ی age) می‌سازد. همه‌ی داده‌ها با همین کلید رمز می‌شوند.
  - کلید اصلی با **عبارت عبور** کاربر (scrypt) قفل می‌شود و نسخه‌ی قفل‌شده‌اش در خود محل ذخیره می‌ماند. سیستم
    دوم فقط عبارت عبور را می‌پرسد؛ هیچ فایلی دستی جابه‌جا نمی‌شود.
  - روی هر سیستم، کلید باز‌شده در keyring سیستم‌عامل نگه داشته می‌شود. چون اجرای پس‌زمینه (systemd) معمولاً به
    keyring دسترسی ندارد، یک فایل کلید با مجوز `0600` هم به‌عنوان جایگزین هست.
  - **کد بازیابی:** موقع init یک کد بازیابی (خود کلید اصلی، به شکل قابل چاپ) یک بار نشان داده می‌شود. فراموش
    کردن عبارت عبور + گم کردن این کد = داده‌ها برنمی‌گردند؛ این صریحاً گفته می‌شود.
  - عوض کردن عبارت عبور فقط قفل کلید اصلی را عوض می‌کند، نه کل داده‌ها را.
  - برای کاربران حرفه‌ای: به‌جای عبارت عبور، یک فایل کلید (اختیاری).
- **جست‌وجوی رمز و توکن قبل از ارسال** با کتابخانه‌ی gitleaks. فایلی که چیزی در آن پیدا شود، روی سیستم می‌ماند
  و در `status` با قانونی که پیدایش کرده نمایش داده می‌شود. اگر این در اجرای پس‌زمینه پیش آمد، در اولین
  `SessionStart` بعدی یک خط به کاربر گفته می‌شود.
- **قانون‌های مجاز** که کاربر می‌تواند روشن کند، مثل آدرس دیتابیس روی `localhost` (در هفته‌ی آزمایشی ۱۶ گفتگو از
  ۲۰ تا فقط به خاطر آدرس دیتابیس محلی توسعه جا ماندند).
- هرگز `.env`، اطلاعات ورود، `~/.claude/.credentials.json` و `~/.claude.json` را نخواند و نفرستد.
- داده‌ی رمزنگاری‌شده هنوز حجم و زمان فایل‌ها را به محل ذخیره نشان می‌دهد؛ این در مستندات گفته شود.

## ۹. تجربه‌ی کاربری

### نسخه‌ی ۱ (لینوکس): خط فرمان

| فرمان | کار |
| ---- | ---- |
| `karvan init` | اجرای اول: انتخاب محل ذخیره، تنظیم رمزنگاری، تعریف پروژه‌ها، نصب hookها و زمان‌بند |
| `karvan status` | آخرین همگام‌سازی، چیزهای منتظر، چیزهای نگه‌داشته و دلیلشان، تداخل‌ها، مشکلات |
| `karvan sync` | همگام‌سازی همین الان |
| `karvan restore [machine]` | بازگردانی کار نیمه‌تمام |
| `karvan doctor` | بررسی درست بودن JSON ی settings.json، hookها، زمان‌بند، دسترسی به محل ذخیره، شبکه (پورت ۲۲/۴۴۳) و نسخه‌ی ساختار اپلیکیشن |
| `karvan uninstall` | حذف hookها و زمان‌بند، برگرداندن تنظیمات، نگه داشتن محل ذخیره |

- پیام‌ها به زبان ساده؛ اول انگلیسی، بعد فارسی.

### بعداً: آیکون کنار ساعت

آیکون وضعیت، «همگام‌سازی همین الان»، «بازگردانی»، تنظیمات. با Wails و همان هسته‌ی Go.

## ۱۰. نصب و انتشار

- لینوکس: بسته‌ی `.deb` و یک فایل فشرده‌ی مستقل؛ یک فایل اجرایی، بدون نیاز به نصب چیز دیگر. ساخت با goreleaser.
- `init` فایل `~/.claude/settings.json` را با احتیاط ویرایش می‌کند: JSON ی نامعتبر را با پیام واضح رد می‌کند،
  نسخه‌ی پشتیبان می‌گیرد و hookهای خودش را فقط یک بار اضافه می‌کند.
- واحدهای کاربری systemd برای زمان‌بند و اجرای موقع خاموش شدن.
- **امضای دیجیتال:** ویندوز (SmartScreen) و مک (Gatekeeper) فایل اجرایی بدون امضا را مسدود می‌کنند. قبل از
  انتشار ویندوز و مک، گواهی امضای ویندوز و حساب توسعه‌دهنده‌ی Apple (notarization) لازم است و هزینه دارد.

## ۱۱. سیستم‌عامل‌ها

| | لینوکس (نسخه‌ی ۱) | ویندوز (بعدی) | مک (بعدتر) |
| -- | -- | -- | -- |
| داده‌ی اپلیکیشن دسکتاپ | `~/.config/Claude` | `%APPDATA%\Claude` | `~/Library/Application Support/Claude` |
| زمان‌بند و اجرای موقع خاموشی | واحدهای کاربری systemd | Task Scheduler (`schtasks.exe`) | launchd |
| محل ذخیره‌ی پیش‌فرض | git | پوشه‌ی فضای ابری | پوشه‌ی فضای ابری |

کد جزئیات هر سیستم‌عامل را پشت یک بسته (package) نگه می‌دارد و هیچ فرمان مخصوص GNU (`date`، `sed`، `tac`،
`flock`) را صدا نمی‌زند.

## ۱۲. ساختارهای مستندنشده و ریسک محصول

- فایل گفتگوها در اپلیکیشن و ساختار متن گفتگوها، ساختارهای داخلی هستند. نسخه‌ی ساختار تشخیص داده می‌شود؛ اگر
  ناشناخته بود، همگام‌سازی همان بخش متوقف می‌شود، بقیه ادامه می‌دهد و به کاربر گفته می‌شود. فقط فیلدهای
  شناخته‌شده نوشته می‌شوند؛ بقیه بدون تغییر منتقل می‌شوند. تست‌ها روی فایل‌های واقعی نسخه‌های فعلی اجرا می‌شوند.
- کد باید طوری باشد که نگهدارنده بتواند ظرف یک ساعت بعد از تغییر ساختار، اصلاحش کند.
- **ریسک محصول:** ممکن است Anthropic خودش همگام‌سازی گفتگوها بین سیستم‌ها را اضافه کند. قبل از هر مرحله‌ی بزرگ
  بررسی شود؛ اگر اضافه کرد، Karvan روی چیزهایی تمرکز می‌کند که آن پوشش نمی‌دهد (مثلاً کار نیمه‌تمام کد).

## ۱۳. معیارهای موفقیت

- هیچ داده‌ای در سناریوهای بخش ۱۵ و یک دوره‌ی آزمایشی دوهفته‌ای از دست نرود؛ هیچ خطی از گفتگو حذف نشود.
- گفتگویی که روی یک سیستم ادامه پیدا کرده، حداکثر ۱۵ دقیقه بعد از آنلاین شدن هر دو سیستم روی سیستم دیگر قابل
  ادامه باشد.
- در استفاده‌ی عادی هیچ ادغام دستی‌ای لازم نباشد.
- از نصب تا اولین همگام‌سازی برای یک برنامه‌نویس کمتر از ۵ دقیقه طول بکشد.

## ۱۴. مراحل

1. **M0 – هم‌ارزی:** خط فرمان Go با رفتار نمونه‌ی bash روی موتور همگام‌سازی جدید (یک پروژه، بدون رمزنگاری)،
   تست‌شده روی همان دو سیستم. فاز به فاز (بخش ۱۴-۱).
2. **M1 – امن:** رمزنگاری، جست‌وجوی رمز و توکن، قانون‌های مجاز، چند پروژه.
3. **M2 – انتشار عمومی لینوکس:** بسته‌بندی، `doctor`، `uninstall`، مستندات.
4. **M3:** محل ذخیره‌ی پوشه‌ی ابری برای عموم، آیکون کنار ساعت.
5. **M4:** ویندوز (با امضای دیجیتال). **M5:** مک (با notarization).

### ۱۴-۱. فازهای M0

هر فاز با تست‌های پاس‌شده، commit و push تمام می‌شود و برای بررسی متوقف می‌شود تا نگهدارنده اجازه‌ی فاز بعد را
بدهد.

0. **مشخصات و آزمایش:** نوشتن `docs/sync-engine.md` (ساختار فهرست‌ها و blobها، قانون‌های ادغام با مثال،
   رفتار با فایل‌های در حال نوشتن، قالب نسخه‌ها). یک آزمایش کوتاه با go-git: fetch و push ی fast-forward به یک
   repo آزمایشی از راه `ssh://git@ssh.github.com:443/...`، و تکرار push بعد از رد شدن.
1. **اسکلت:** `go mod`، خط فرمان (`init`، `sync`، `status`، `restore`، `doctor` به‌صورت stub)، فایل تنظیمات،
   بسته‌ی مسیرها (پوشه‌های Claude، اسم پوشه‌ی پروژه)، CI با `go test`، `go vet`، `golangci-lint` و ساخت
   آزمایشی goreleaser.
2. **Hookها:** `init` hookهای `SessionStart` و `SessionEnd` را با احتیاط به `settings.json` اضافه می‌کند؛
   `doctor` بررسی‌شان می‌کند.
3. **هسته‌ی موتور:** فهرست‌ها، blobها، قانون‌های ادغام، قفل، و محل ذخیره‌ی پوشه‌ی محلی (برای تست).
4. **محل ذخیره‌ی git:** با go-git، طبق بخش ۷.
5. **فایل‌های مشترک:** `CLAUDE.md`، مهارت‌ها (به‌جز `synced/`)، حافظه‌ی پروژه، `CLAUDE.machine.md`.
6. **متن گفتگوها:** بازه‌ی تاریخچه، ترکیب خطوط، فایل‌های در حال نوشتن، نگه داشتن فایل‌های دارای رمز.
7. **فهرست گفتگوهای اپلیکیشن:** نشانگر مسیر، جدیدتر برنده، رفتار وقتی اپلیکیشن باز است.
8. **کار نیمه‌تمام:** ذخیره، وضعیت، بازگردانی.
9. **زمان‌بند و تست کامل:** واحدهای systemd؛ تست کامل با دو پوشه‌ی خانگی موقت و یک repo ی bare محلی.

## ۱۵. سناریوهای تست (از هفته‌ی آزمایشی و شورا)

1. یک گفتگو روی هر دو سیستم ادامه پیدا کرده ← خطوط هر دو طرف می‌مانند، چیزی متوقف نمی‌شود.
2. شاخه‌ی تازه بدون commit خودش ← بازگردانی هر چه لازم دارد را می‌گیرد.
3. ارسال روی پورت ۲۲ گیر می‌کند ← تشخیص داده می‌شود و ۴۴۳ پیشنهاد می‌شود.
4. `settings.json` با کامای اضافه ← خطای واضح، هیچ چیزی نوشته نمی‌شود.
5. فایل گفتگوها وقتی اپلیکیشن باز است می‌رسند ← بعد از Ctrl+Q و باز کردن دوباره نمایش داده می‌شوند؛ فایل‌های
   موجود بازنویسی نمی‌شوند.
6. رمز یا توکن در متن گفتگو ← نگه داشته می‌شود، فهرست می‌شود، هرگز ارسال نمی‌شود.
7. یک سیستم یک روز خاموش است، بعد هر دو آنلاین می‌شوند ← بدون کار دستی به یک وضعیت می‌رسند.
8. merge یا rebase در جریان در پروژه ← ذخیره نمی‌شود و دلیلش گفته می‌شود.
9. گفتگو وسط نوشته شدن کپی می‌شود ← خط نیمه‌کاره کنار گذاشته می‌شود، دور بعد کامل می‌آید.
10. دو سیستم همزمان push می‌کنند ← یکی رد می‌شود، دوباره fetch و ادغام می‌کند و push می‌کند؛ چیزی گم نمی‌شود.
11. اجرای پس‌زمینه بدون keyring ← از فایل کلید `0600` استفاده می‌کند.

## ۱۶. تصمیم‌ها

1. اسم: Karvan.
2. مجوز انتشار: MIT یا Apache-2.0.
3. کلید رمزنگاری: کلید اصلی تصادفی قفل‌شده با عبارت عبور، کد بازیابی، فایل کلید `0600` برای اجرای پس‌زمینه؛
   فایل کلید به‌جای عبارت عبور اختیاری (بخش ۸).
4. بازه‌ی تاریخچه: قابل تنظیم، پیش‌فرض ۷ روز.
5. git: داخل برنامه (go-git)، فقط به‌عنوان انبار؛ کاربر چیزی نصب نمی‌کند (بخش ۷).
6. تنظیمات هر سیستم: پیش‌فرض همه مشترک؛ `CLAUDE.machine.md` و حذف برای یک سیستم (بخش ۴-۱).
7. زبان برنامه: Go (بخش ۱۷).
8. موتور همگام‌سازی مال خود Karvan است، نه ادغام git (بخش ۶).
9. زبان مستندات: فارسی. کد، commitها و پیام‌های commit: انگلیسی.

## ۱۷. انتخاب زبان (شورای مشاوران، ۱۴۰۵/۰۸/۲۵)

پنج مشاور با پنج نگاه متفاوت (منتقد، اصول اولیه، فرصت‌جو، تازه‌وارد، اجراکننده) جداگانه نظر دادند و بعد جواب‌های
هم را بی‌نام نقد کردند.

- **همه Go را انتخاب کردند.** `age` و `gitleaks` خودشان با Go نوشته شده‌اند، پس بخش‌های امنیتی از کتابخانه‌های
  جاافتاده می‌آیند نه از کد تازه. ساخت برای همه‌ی سیستم‌عامل‌ها با یک فرمان انجام می‌شود. خواندن Go برای یک
  برنامه‌نویس TypeScript حدود دو هفته جا می‌افتد.
- **Rust کنار رفت:** نگهدارنده نمی‌تواند کدش را بررسی و اشکال‌یابی کند. **Python کنار رفت:** آنتی‌ویروس‌های
  ویندوز فایل اجرایی‌اش را زیاد به‌اشتباه می‌گیرند. **TypeScript کنار رفت:** کتابخانه‌ی git آن SSH ندارد و فایل
  اجرایی ۶۰ تا ۹۰ مگابایت می‌شود.
- **مهم‌ترین نتیجه از زبان مهم‌تر بود:** git نمی‌تواند فایل رمزنگاری‌شده را ادغام کند، پس موتور همگام‌سازی باید
  مال خود Karvan باشد (بخش ۶). با این طراحی، ضعف‌های go-git (نداشتن ادغام کامل) اهمیتی ندارند.
- نقطه‌های کوری که شورا پیدا کرد و به این PRD اضافه شد: ترکیب خطوط گفتگو به‌جای «بلندتر برنده است»، فایل‌های
  در حال نوشتن، فایل کلید برای اجرای پس‌زمینه، امضای دیجیتال، مسیرهای ویندوز، ریسک محصول، و پاک کردن رمزی که
  اشتباهی فرستاده شده.
