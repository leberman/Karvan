# مشخصات موتور همگام‌سازی Karvan

- وضعیت: پیش‌نویس ۱ (فاز ۰)، ۱۴۰۵/۰۸/۲۵ (2026-11-16)
- مرجع بالادستی: `docs/PRD.md` بخش‌های ۵، ۶، ۷، ۱۲ و ۱۵
- نسخه‌ی قالب محل ذخیره که این سند تعریف می‌کند: **۱** (M0، بدون رمزنگاری)

این سند دقیقاً می‌گوید فازهای ۳ تا ۸ ی M0 چه چیزی را پیاده می‌کنند. هر جا کد با این سند فرق کند، یکی از دو
تا باید اصلاح شود؛ تصمیم‌های تازه اول این‌جا نوشته می‌شوند. کلمه‌های «باید» و «نباید» الزام‌اند.

## ۰. اصل‌ها در یک نگاه

1. **محل ذخیره فقط انبار است.** چهار عمل: `put`، `get`، `list` و نوشتن شرطی. هیچ منطق ادغامی در محل ذخیره
   نیست و هیچ‌وقت از ادغام git استفاده نمی‌شود.
2. **محتوا با اثر انگشتش نام‌گذاری می‌شود** (content-addressed). blob نوشته‌شده هرگز عوض نمی‌شود؛ پس نوشتن
   همزمان دو سیستم روی یک blob بی‌خطر است.
3. **هر سیستم فقط فهرست (manifest) خودش را می‌نویسد.** هیچ دو سیستمی هرگز یک فایل قابل‌تغییر را در محل ذخیره
   نمی‌نویسند.
4. **تصمیم از روی تاریخچه‌ی اثر انگشت‌ها گرفته می‌شود، نه ساعت.** ساعت فقط برای شکستن تساوی و برای قانون‌های
   محلی (۱۵ دقیقه، ۷ روز) به کار می‌رود.
5. **ادغام قطعی (deterministic) است:** هر سیستمی که همان ورودی‌ها را ببیند، دقیقاً همان بایت‌ها را می‌سازد. برای
   همین دو سیستمی که همزمان ادغام می‌کنند به یک نتیجه می‌رسند و دور بعد چیزی برای ادغام نمی‌ماند.
6. **هیچ چیز بی‌صدا گم نمی‌شود:** هیچ خطی از گفتگو حذف نمی‌شود؛ در تداخل متن، هر دو نسخه می‌مانند.

## ۱. واژه‌ها

| واژه | معنی |
| ---- | ---- |
| سیستم (machine) | یک نصب Karvan با اسم یکتا (مثلاً `work`، `home`). اسم: حروف کوچک لاتین، رقم و `-`، حداکثر ۳۲ نویسه. |
| مسیر منطقی | اسم یک فایل مستقل از سیستم، مثل `global/CLAUDE.md` (بخش ۴). |
| نسخه | محتوای نرمال‌شده‌ی یک فایل (بخش ۳-۱)؛ با اثر انگشتش شناخته می‌شود. |
| blob | یک تکه (chunk) از محتوای یک نسخه، فشرده، در محل ذخیره. |
| فهرست (manifest) | فایلی که یک سیستم در محل ذخیره می‌نویسد: وضعیت همه‌ی مسیرهای منطقی از نگاه آن سیستم. |
| وضعیت محلی | فایل‌های Karvan روی خود سیستم (`~/.local/state/karvan/`)؛ هرگز ارسال نمی‌شوند. |
| دور (run) | یک بار اجرای چرخه‌ی بخش ۷. |

## ۲. ساختار محل ذخیره

```text
<store root>/
  FORMAT                          # JSON ی کوچک، همیشه بدون رمز (بخش ۱۲)
  manifests/
    <machine>.krv                 # فهرست هر سیستم، در پوشش (envelope) ی بخش ۳-۳
  blobs/
    <hh>/<hash-hex>               # hh = دو نویسه‌ی اول hash؛ هر فایل یک تکه در پوشش بخش ۳-۳
  keys/                           # از M1: کلید اصلی قفل‌شده با عبارت عبور (PRD ۸)
  gc/
    <machine>.krv                 # دفترچه‌ی پاک‌سازی (بخش ۱۰)
```

- `FORMAT` اولین چیزی است که خوانده و آخرین چیزی است که موقع ساختن محل ذخیره نوشته می‌شود.
- اسم فایل‌ها فقط از `[a-z0-9-]` و پسوند ثابت است. هر فایل دیگری (مثلاً «conflicted copy» ی Dropbox یا
  `.sync-conflict-` ی Syncthing) **نادیده گرفته می‌شود** و اگر به اسم یکی از فهرست‌ها شبیه بود، در `status`
  گزارش می‌شود.
- پوشه‌ی دو نویسه‌ای فقط برای این است که هیچ پوشه‌ای ده‌ها هزار فایل نداشته باشد.
- **چیزهایی که بعداً اضافه می‌شوند** بدون تغییر این ساختار: `keys/` (M1)، رمزنگاری داخل پوشش blobها و
  فهرست‌ها (M1)، فایل‌های تازه در ریشه با اسم جدید. خواننده‌ای که پوشه یا فایلی را در ریشه نمی‌شناسد، آن را
  نادیده می‌گیرد (نه خطا).

## ۳. اثر انگشت، تکه‌ها، فشرده‌سازی، پوشش

### ۳-۱. محتوای نرمال‌شده

اثر انگشت روی **محتوای نرمال‌شده** گرفته می‌شود، یعنی بعد از:

- جایگزینی مسیر پروژه با نشانگر، فقط در جاهایی که بخش ۸-۱ و ۸-۲ می‌گویند؛
- برای متن گفتگو: کنار گذاشتن خط آخر اگر به `\n` ختم نشده (بخش ۹).

پس دو سیستم با مسیرهای متفاوت برای یک گفتگوی یکسان، اثر انگشت یکسان دارند.

### ۳-۲. اثر انگشت و تکه‌ها

- **الگوریتم:** SHA-256 (کتابخانه‌ی استاندارد Go، روی پردازنده‌های امروزی شتاب سخت‌افزاری دارد). نوشتار:
  `sha256:<64 hex>`.
- **اثر انگشت نسخه** = SHA-256 ی کل محتوای نرمال‌شده. هویت نسخه همین است و به نحوه‌ی تکه‌کردن بستگی ندارد.
- **تکه‌ها:** هر نسخه به یک یا چند تکه تقسیم می‌شود و هر تکه یک blob است با اسم SHA-256 ی خود تکه.
  - فایل تا ۵۱۲ کیلوبایت: یک تکه (اثر انگشت تکه = اثر انگشت نسخه).
  - فایل بزرگ‌تر **متنی** (هر فایلی که `\n` دارد، از جمله متن گفتگو): مرز تکه همیشه بعد از یک `\n` است. بعد از
    هر خط، اگر طول تکه‌ی فعلی ≥ ۲۵۶ کیلوبایت باشد و بایت اول SHA-256 ی همان خط `& 0x07 == 0` باشد، تکه بسته
    می‌شود؛ اگر طول تکه به ۲ مگابایت رسید، در اولین `\n` بسته می‌شود؛ اگر ۴ مگابایت بدون `\n` گذشت، همان‌جا
    بریده می‌شود.
  - فایل بزرگ‌تر بدون `\n`: تکه‌های ثابت ۱ مگابایتی.
- **چرا تکه:** متن گفتگو مدام بلندتر می‌شود. بدون تکه، هر دور یک کپی کامل و تازه از کل فایل ارسال و در
  تاریخچه‌ی git برای همیشه نگه داشته می‌شد (فشرده/رمزنگاری‌شده است، پس git نمی‌تواند delta بگیرد). با
  مرزهای وابسته به محتوا، اضافه شدن خط فقط تکه‌ی آخر را عوض می‌کند و ادغام دو شاخه فقط تکه‌های اطراف محل
  تفاوت را.
- عوض کردن این قاعده فقط اسم blobها را عوض می‌کند، نه درستی را؛ با این حال جزو قالب نسخه‌ی ۱ است.

### ۳-۳. پوشش (envelope) و فشرده‌سازی

هر blob و هر فایل فهرست این شکل را دارد:

```text
offset  size  value
0       4     "KRVN"                 magic
4       1     0x01                   envelope version
5       1     codec:  0 = none, 1 = zstd
6       1     cipher: 0 = none, 1 = age (M1)
7       1     0x00                   reserved
8       ...   payload = cipher( codec( content ) )
```

- **فشرده‌سازی:** zstd (کتابخانه‌ی `github.com/klauspost/compress/zstd`، Go ی خالص)، سطح پیش‌فرض. اگر خروجی
  فشرده بزرگ‌تر از ورودی شد، `codec = 0`.
- **جای رمزنگاری (M1):** `cipher = 1` و payload یک فایل age است که داخلش داده‌ی فشرده است. ساختار پوشه‌ها و
  فهرست‌ها عوض نمی‌شود. دو چیز در M1 عوض می‌شود و برای همین M1 قالب را به **۲** می‌برد:
  - اسم blob و اثر انگشت‌ها به **HMAC-SHA256** با کلیدی مشتق از کلید اصلی تبدیل می‌شود؛ وگرنه کسی که به محل
    ذخیره دسترسی دارد می‌تواند حدس بزند «آیا فایل X این‌جاست» (حمله‌ی تأیید).
  - فهرست‌ها هم رمزنگاری می‌شوند (اسم پروژه‌ها و گفتگوها را نشان می‌دهند).
- خواندن هر blob با بررسی اثر انگشتش تمام می‌شود. blob ی خراب یا نیمه‌کاره (مثلاً پوشه‌ی ابری هنوز کاملش نکرده)
  «موجود نیست» حساب می‌شود: آن مسیر به دور بعد می‌رود، بقیه ادامه می‌دهند.

## ۴. مسیرهای منطقی

| مسیر منطقی | فایل روی لینوکس | نوع (`kind`) |
| ---- | ---- | ---- |
| `global/CLAUDE.md` | `~/.claude/CLAUDE.md` | `text` |
| `global/skills/<name>/<rel>` | `~/.claude/skills/<name>/<rel>` (به‌جز `synced/`) | `text` یا `binary` |
| `project:<pid>/memory/<rel>` | `~/.claude/projects/<dashed>/memory/<rel>` | `text` |
| `project:<pid>/transcripts/<session>.jsonl` | `~/.claude/projects/<dashed>/<session>.jsonl` | `transcript` |
| `project:<pid>/transcripts/<session>/subagents/<file>.jsonl` | `.../<dashed>/<session>/subagents/<file>.jsonl` | `transcript` |
| `project:<pid>/transcripts/<session>/tool-results/<file>` | `.../<dashed>/<session>/tool-results/<file>` | `immutable` |
| `project:<pid>/desktop/<account>/<org>/<local_id>.json` | `~/.config/Claude/claude-code-sessions/<account>/<org>/<local_id>.json` | `desktop` |
| `folder:<name>/<rel>` | پوشه‌ی شخصی که کاربر انتخاب کرده | `text` یا `binary` |
| `machine:<name>/wip/<pid>/...` | (تولید Karvan؛ PRD ۶-۵) | `owned` |
| `machine:<name>/held.json` | (فهرست نگه‌داشته‌ها؛ از M1) | `owned` |

- `<pid>` شناسه‌ی پروژه است: `p-` + ۱۶ نویسه‌ی اول hex ی SHA-256 ی شناسه‌ی کامل پروژه (آدرس remote ی
  یکسان‌شده، مثل `github.com/owner/app`، یا `name:<اسم>` برای پروژه‌ی بدون remote). شناسه‌ی کامل و اسم قابل
  نمایش در جدول `projects` ی فهرست است. این کار `/` و نویسه‌های عجیب را از مسیر بیرون نگه می‌دارد.
- `<rel>` همیشه با `/` نوشته می‌شود، نرمال (بدون `.` و `..`، بدون `/` ی اول)، به همان شکل بزرگ و کوچک حروف
  روی دیسک. روی ویندوز (بعداً) دو مسیر که فقط در بزرگی حروف فرق دارند، تداخل حساب می‌شوند.
- `<session>` و `<local_id>` همان اسم فایل‌اند (UUID / `local_<id>`) و دست نمی‌خورند.
- فایل‌های `CLAUDE.machine.md`، `settings.json`، `.credentials.json`، `~/.claude.json` و `.env` هیچ‌وقت مسیر
  منطقی ندارند (PRD ۴ و ۸).
- symlinkها دنبال نمی‌شوند و منتقل نمی‌شوند (در `status` گفته می‌شود).
- نوع‌ها:
  - `text`: ادغام سه‌طرفه (۸-۳). `binary`: مثل text ولی بدون ادغام محتوا (تداخل = دو نسخه کنار هم).
  - `transcript`: ترکیب خطوط (۸-۱). `desktop`: جدیدتر برنده (۸-۲).
  - `immutable`: فقط یک بار نوشته می‌شود؛ اگر دو نسخه‌ی متفاوت دید، بزرگ‌تر می‌ماند و گزارش می‌شود.
  - `owned`: فقط سیستم صاحبش می‌نویسد؛ هیچ‌وقت ادغام نمی‌شود و روی دیسک بقیه نوشته نمی‌شود (۸-۵).

## ۵. فهرست (manifest)

### ۵-۱. ساختار

محتوای داخل پوشش، JSON با UTF-8 (کلیدها مرتب، برای اینکه خروجی قطعی باشد):

```json
{
  "format": 1,
  "machine": "work",
  "machineId": "6f1c0d0e-3a52-4c55-9d2c-0b8f1e7a9c11",
  "karvan": "0.1.0",
  "seq": 418,
  "writtenAt": "2026-11-16T17:42:10Z",
  "seen": { "home": 377 },
  "projects": {
    "p-3fa1c2d4e5f60718": { "id": "github.com/owner/app", "name": "app" }
  },
  "entries": {
    "global/CLAUDE.md": {
      "kind": "text",
      "hash": "sha256:9b1f…",
      "size": 2210,
      "mtime": "2026-11-16T09:12:03Z",
      "chunks": ["sha256:9b1f…"],
      "history": ["sha256:51aa…", "sha256:07c2…"],
      "changedAt": "2026-11-16T09:14:00Z"
    },
    "project:p-3fa1c2d4e5f60718/transcripts/0b7e…c3.jsonl": {
      "kind": "transcript",
      "hash": "sha256:e40d…",
      "size": 1873320,
      "mtime": "2026-11-16T17:39:51Z",
      "chunks": ["sha256:aa01…", "sha256:aa02…", "sha256:c9f3…"],
      "history": ["sha256:1d2e…"],
      "changedAt": "2026-11-16T17:42:09Z",
      "lines": 1290,
      "schema": "cc-jsonl"
    },
    "global/skills/old-skill/SKILL.md": {
      "kind": "text",
      "deleted": true,
      "history": ["sha256:77e0…"],
      "changedAt": "2026-11-15T20:00:00Z"
    }
  }
}
```

| فیلد | معنی |
| ---- | ---- |
| `format` | نسخه‌ی قالب (بخش ۱۲). |
| `machine`، `machineId` | اسم سیستم و یک UUID تصادفی که `init` می‌سازد. اسم فایل فهرست = `machine`. اگر فایلی با این اسم ولی `machineId` ی دیگر هست، یعنی دو سیستم یک اسم دارند: توقف و گزارش. |
| `seq` | شمارنده‌ای که با هر بار نوشتن فهرست یکی زیاد می‌شود. در وضعیت محلی هم نگه داشته می‌شود (بخش ۷، ۱۳). |
| `writtenAt` | ساعت این سیستم موقع نوشتن (فقط برای نمایش و تشخیص اختلاف ساعت، بخش ۱۱). |
| `seen` | `seq` ی فهرست هر سیستم دیگر که این دور دیده و لحاظ کرده. `status` از این می‌فهمد «home آخرین بار کِی تغییرات من را دیده». |
| `projects` | جدول `<pid>` ← شناسه‌ی کامل و اسم. مسیر محلی پروژه **این‌جا نیست** (مال وضعیت محلی است). |
| `entries` | یک ورودی برای هر مسیر منطقی که این سیستم دنبال می‌کند. |

فیلدهای هر ورودی:

| فیلد | معنی |
| ---- | ---- |
| `kind` | بخش ۴. |
| `hash` | اثر انگشت نسخه‌ی فعلی روی دیسک این سیستم (بعد از نرمال‌سازی). در ورودی حذف‌شده نیست. |
| `size` | حجم محتوای نرمال‌شده، بایت. |
| `mtime` | زمان تغییر فایل روی دیسک این سیستم (فقط اطلاع؛ تصمیم با آن گرفته نمی‌شود، به‌جز ۸-۳ برای انتخاب نسخه‌ی اصلی در تداخل). |
| `chunks` | اثر انگشت تکه‌ها به ترتیب. |
| `history` | اجداد این نسخه، جدیدترین اول، بدون خود `hash`: نسخه‌هایی که این نسخه از آن‌ها ساخته شده (بخش ۵-۲). سقف: ۶۴ برای `text`/`binary`/`desktop`، ۸ برای `transcript`/`immutable`. |
| `deleted` | سنگ قبر (tombstone): این سیستم فایل را داشت و حالا ندارد. `history[0]` آخرین نسخه‌ای است که پاک شد. |
| `retired` | این سیستم دیگر این مسیر را دنبال نمی‌کند (مثلاً گفتگو از بازه‌ی ۷ روزه بیرون رفت). **حذف نیست** و به بقیه منتقل نمی‌شود. |
| `held` | (M1) فایل روی این سیستم نگه داشته شده (مثلاً رمز پیدا شد). بقیه آن را مثل `retired` می‌بینند. |
| `historyChunks` | فقط برای `text`: اثر انگشت → تکه‌ها، برای حداکثر ۸ نسخه‌ی آخر `history`، تا blobهای پایه‌ی ادغام سه‌طرفه پاک نشوند (بخش ۱۰). |
| `changedAt` | ساعت این سیستم وقتی این ورودی آخرین بار عوض شد. |
| `lines`، `schema` | فقط برای `transcript`: تعداد خطوط و قالب تشخیص‌داده‌شده (بخش ۱۲). |

### ۵-۲. «نسخه‌ی پایه» و تاریخچه

PRD برای هر مسیر یک «hash ی نسخه‌ی پایه» می‌خواهد. با بیش از دو سیستم یک پایه کافی نیست (پایه‌ی من با home
ممکن است با پایه‌ی من با laptop فرق کند). برای همین هر ورودی فهرست کوتاهی از اجداد دارد (`history`) و پایه از
روی آن محاسبه می‌شود:

- **تغییر محلی** از `h1` به `h2`: `hash = h2`، `history = [h1] + history_قبلی`.
- **گرفتن نسخه‌ی دیگری** (`R` بر `L` غالب است): `hash = R.hash`، `history = R.history` (که `L.hash` را دارد).
- **ادغام** `L` و `R` به `M`: `hash = M`، `history = [L.hash, R.hash] + یکی‌درمیان(L.history, R.history)` بدون
  تکرار، تا سقف.
- **غالب بودن:** `X` بر `Y` غالب است اگر `Y.hash ∈ X.history` (یعنی X از Y ساخته شده).
- **پایه‌ی ادغام** `L` و `R`: اولین اثر انگشت در `[L.hash] + L.history` که در `{R.hash} ∪ R.history` هم هست. اگر
  نبود (تاریخچه از سقف گذشته)، پایه‌ای وجود ندارد.

تاریخچه فقط وقتی جلو می‌رود که اثر انگشت واقعاً عوض شود، پس سقف ۶۴ یعنی ۶۴ نسخه‌ی متفاوت بین دو همگام‌سازی، نه
۶۴ دور.

## ۶. وضعیت محلی

در `~/.local/state/karvan/` (روی ویندوز و مک معادلش؛ از بسته‌ی مسیرها):

| فایل | محتوا |
| ---- | ---- |
| `manifest.json` | آخرین فهرست خود این سیستم (همان که آخرین بار در محل ذخیره نوشته شد یا باید نوشته شود)، به‌علاوه‌ی `publishedSeq`. |
| `scan-cache.json` | برای هر فایل: مسیر، حجم، زمان تغییر، inode و اثر انگشت؛ اگر این‌ها عوض نشده، دوباره hash گرفته نمی‌شود. |
| `projects.json` | `<pid>` ← مسیر محلی پروژه روی این سیستم (PRD ۵). |
| `lock` | قفل (بخش ۹-۶). |
| `pending.json` | مسیرهایی که این دور نوشته نشدند (گفتگوی باز، اپلیکیشن باز) و دلیلشان، برای `status`. |
| `log/` | لاگ چرخشی. |

`~/.cache/karvan/` نسخه‌ی محلی محل ذخیره‌ی git و blobهای اخیر را دارد؛ پاک کردنش بی‌خطر است.

## ۷. چرخه‌ی همگام‌سازی

```text
 0. قفل      1. FORMAT     2. خواندن فایل‌ها    3. گرفتن فهرست‌ها
 4. تصمیم    5. نوشتن محلی 6. ارسال blobها      7. نوشتن شرطی فهرست   8. پایان
                                                     │ رد شد
                                                     └──► 3 (حداکثر ۵ بار)
```

0. **قفل** (بخش ۹-۶). اجرای زمان‌بند اگر قفل گرفته است، بی‌صدا تمام می‌شود.
1. **`FORMAT`** را بخوان (git: بعد از fetch). اگر نبود: محل ذخیره راه‌اندازی نشده؛ فقط `init` آن را می‌سازد.
   اگر قالب ناشناخته بود: بخش ۱۲.
2. **خواندن فایل‌های محلی و به‌روز کردن فهرست خودم (در حافظه):**
   - همه‌ی منبع‌های روشن را بگرد (PRD ۴)، با فیلترها: بازه‌ی ۷ روزه برای گفتگوها (بر اساس زمان تغییر فایل)،
     حذف‌های مخصوص این سیستم (PRD ۴-۱)، و در اجرای زمان‌بند، گفتگوهایی که در ۱۵ دقیقه‌ی اخیر نوشته شده‌اند
     (بخش ۹-۳).
   - هر فایل را با روش امن بخوان (۹-۱)، نرمال کن (۳-۱)، hash بگیر (یا از `scan-cache` بردار).
   - اثر انگشت متفاوت از ورودی فهرست ← ورودی تازه با تاریخچه‌ی جلو رفته (۵-۲).
   - فایلی که در فهرست بود و دیگر روی دیسک نیست ← `deleted` (برای `text`/`binary`) یا `retired` (برای
     `transcript`، `desktop`، `immutable`؛ این‌ها را Claude خودش پاک می‌کند، مثلاً با `cleanupPeriodDays`، و پاک
     شدنشان نباید به سیستم‌های دیگر سرایت کند).
   - گفتگویی که از بازه بیرون رفته ← `retired`.
3. **گرفتن فهرست‌های بقیه:** `list manifests/` و `get` هر کدام (git: یک fetch). فهرست خودم را هم بخوان و
   بررسی کن (بخش ۱۳-۲: `seq` و `machineId`).
4. **تصمیم برای هر مسیر** (بخش ۸) روی اجتماع مسیرهای همه‌ی فهرست‌ها. ورودی‌های `retired`/`held` ی بقیه، و
   ورودی‌های با `kind` ی ناشناخته، نادیده گرفته می‌شوند. اگر مسیری در فهرست بقیه هست و در فهرست من نیست ولی
   فایلش روی دیسک من هست (مثلاً گفتگوی قدیمی‌ای که حالا روی سیستم دیگر ادامه پیدا کرده)، همان‌جا خوانده و
   مثل یک نسخه‌ی محلی وارد تصمیم می‌شود. نتیجه برای هر مسیر یکی از این‌هاست: هیچ، نوشتن نسخه‌ی R، نوشتن
   نتیجه‌ی ادغام، حذف، ساختن فایل تداخل.
5. **نوشتن محلی:** blobهای لازم را `get` کن، نتیجه را بساز، با قانون‌های بخش ۹ بنویس (فایل موقت + rename،
   قبلش دوباره بررسی که فایل در این فاصله عوض نشده). مسیری که الان نمی‌شود نوشت (گفتگوی باز، اپلیکیشن باز)
   ورودی‌اش در فهرست من **همان نسخه‌ی محلی قبلی** می‌ماند و به `pending.json` می‌رود؛ دور بعد دوباره تصمیم
   گرفته می‌شود. ورودی مسیرهایی که نوشته شدند، اثر انگشت جدید را می‌گیرند.
6. **ارسال blobهای تازه:** هر تکه‌ای که فهرست جدید من به آن اشاره می‌کند و در محل ذخیره نیست، `put` می‌شود
   (در git: به commit اضافه می‌شود). blob همیشه **قبل از** فهرستی که به آن اشاره می‌کند می‌رسد؛ پس هیچ
   فهرستی به blob ی ناموجود اشاره نمی‌کند (جز در پوشه‌ی ابری که ترتیب رسیدن را تضمین نمی‌کند؛ ۳-۳ همین را
   پوشش می‌دهد). ارسال بزرگ در دسته‌های حداکثر ۳۲ مگابایتی انجام می‌شود (یافته‌ی آزمایش go-git).
7. **نوشتن شرطی فهرست:** `seq` یکی زیاد، `seen` و `writtenAt` به‌روز، و نوشتن با این شرط که محل ذخیره از
   مرحله‌ی ۳ عوض نشده باشد (git: push ی fast-forward روی همان commit؛ پوشه: بخش ۱۳-۳). اول در وضعیت محلی
   (`manifest.json`) ذخیره می‌شود، بعد ارسال.
   - **اگر شرط برقرار نبود** (سیستم دیگری در این فاصله فهرستش را نوشت): برگرد به مرحله‌ی ۳ با فهرست‌های تازه،
     دوباره تصمیم بگیر (فقط مسیرهایی که در فهرست‌های تازه عوض شده‌اند فرق می‌کنند)، مرحله‌ی ۵ و ۶ را برای همان‌ها
     انجام بده و دوباره بنویس. حداکثر ۵ بار با فاصله‌ی تصادفی رو به افزایش (۰٫۲ ثانیه × ۲ⁿ، با jitter).
   - **اگر ۵ بار نشد** یا شبکه قطع بود: دور با پیام «ارسال نشد، دوباره امتحان می‌شود» تمام می‌شود. چیزی که در
     مرحله‌ی ۵ روی دیسک نوشته شده بی‌خطر است، چون فهرست محلی آن را ثبت کرده و دور بعد همان را می‌فرستد.
   - **هرگز** نوشتن غیرشرطی یا force push برای «حل» این وضعیت انجام نمی‌شود.
8. **پایان:** `status` به‌روز، پاک‌سازی اگر وقتش است (بخش ۱۰)، آزاد کردن قفل.

**نتیجه‌ی مهم:** چون هر سیستم فقط فایل خودش و blobهای با اسم یکتا را اضافه می‌کند، «رد شدن» هیچ‌وقت تداخل
واقعی در محل ذخیره نیست؛ فقط یعنی «فهرست‌های تازه‌تری هست، دوباره تصمیم بگیر».

## ۸. تصمیم برای هر مسیر

برای مسیر `p`: `L` = ورودی من (بعد از مرحله‌ی ۲)، `R₁…Rₙ` = ورودی‌های فعال سیستم‌های دیگر.

1. نسخه‌های تکراری (اثر انگشت یکسان، یا هر دو `deleted` با یک `history[0]`) یکی می‌شوند.
2. هر نسخه‌ای که نسخه‌ی دیگری بر آن غالب است (۵-۲) کنار می‌رود.
3. اگر یک نسخه ماند: اگر `L` است، کاری نیست؛ وگرنه همان نسخه نوشته (یا حذف) می‌شود.
4. اگر بیش از یکی ماند (تغییر همزمان): ادغام با قانون `kind` آن مسیر (پایین). با بیش از دو نسخه، ادغام دوبه‌دو
   به ترتیب اثر انگشت (کوچک‌تر اول) انجام می‌شود تا نتیجه قطعی باشد.

### ۸-۱. متن گفتگو (`transcript`): ترکیب خطوط

#### ساختار واقعی (بررسی‌شده روی Claude Code ی آبان ۱۴۰۵)

هر خط یک شیء JSON است با فیلد `type`. انواعی که دیده شد:

| `type` | `uuid` | `parentUuid` | `timestamp` | توضیح |
| ---- | ---- | ---- | ---- | ---- |
| `user` | دارد | دارد (اولی `null`) | دارد | پیام کاربر یا نتیجه‌ی ابزار؛ `message.role`، `message.content` |
| `assistant` | دارد | دارد | دارد | هر بلوک محتوا یک خط جدا با `uuid` ی خودش؛ خطوط یک پاسخ API همان `message.id` و `requestId` را دارند |
| `attachment` | دارد | دارد | دارد | ضمیمه‌ها (`attachment.type`: محیط، مدل، فهرست ابزارها، تاریخ و...) |
| `system` | دارد | دارد یا `null` | دارد | مثلاً مرز فشرده‌سازی (`subtype`)، با `logicalParentUuid` |
| `last-prompt` | **ندارد** | ندارد | ندارد | `leafUuid` و `lastPrompt` |
| `queue-operation` | **ندارد** | ندارد | دارد | `operation` (enqueue / dequeue) |
| `atis-latch`، `tools-used` | **ندارد** | ندارد | ندارد | وضعیت داخلی |
| (قدیمی‌تر) `summary`، `file-history-snapshot` | **ندارد** | ندارد | گاهی | `leafUuid` یا `messageId` |

فیلدهای مشترک خطوط پیام: `uuid`، `parentUuid`، `sessionId`، `timestamp` (ISO-8601 با میلی‌ثانیه، UTC)، `cwd`،
`gitBranch`، `version` (نسخه‌ی Claude Code)، `isSidechain`، `userType`، `entrypoint`.

مشاهده‌های مهم برای الگوریتم:

- **همه‌ی خطوط `uuid` ندارند**؛ و خطوط بی‌`uuid` گاهی با محتوای کاملاً یکسان چند بار در یک فایل تکرار می‌شوند
  (مثل `atis-latch`).
- **ترتیب زمانی دقیق نیست:** دو خط پشت سر هم دیده شد که دومی یک میلی‌ثانیه زودتر از اولی است. پس ترتیب فایل
  مرجع است و `timestamp` فقط برای شکستن تساوی.
- زنجیره‌ی `parentUuid` با ترتیب فایل جور است: هر خط پیام به خطی اشاره می‌کند که قبل از آن در فایل آمده.
- گفتگوهای subagent فایل‌های جدا دارند و خروجی‌های بزرگ ابزارها در `<session>/tool-results/` ذخیره می‌شوند
  (برای همین این‌ها هم مسیر منطقی دارند، بخش ۴).

#### کلید هر خط

- خط با `uuid`: کلید = `u:<uuid>`.
- خط بی‌`uuid`: کلید = `h:<anchor>:<sha256(line)>:<n>` که `anchor` = `uuid` ی نزدیک‌ترین خط **قبلی** همان فایل که
  `uuid` دارد (یا `^` اگر نیست) و `n` = شماره‌ی تکرار همین محتوا بعد از همان anchor (از ۰). چون دو سیستم تا نقطه‌ی
  جدا شدن فایل یکسانی دارند، خطوط بی‌`uuid` ی بخش مشترک کلید یکسان می‌گیرند و تکراری حساب می‌شوند، و خطوط بعد
  از جدا شدن (با anchor ی متفاوت) هر دو می‌مانند.
- خطی که JSON ی معتبر نیست: مثل خط بی‌`uuid` با کلید محتوایش (دور ریخته نمی‌شود).
- اگر یک کلید در دو نسخه با بایت‌های متفاوت آمد (نباید پیش بیاید؛ Claude Code خط نوشته‌شده را عوض نمی‌کند):
  نسخه‌ی بلندتر، و در تساوی، آن که از نظر بایتی بزرگ‌تر است؛ در لاگ ثبت می‌شود.

#### الگوریتم ادغام

ورودی: دو (یا چند) نسخه‌ی یک فایل، هر کدام فهرست مرتبی از خطوط.

1. **میان‌بر (حالت معمول):** اگر دنباله‌ی کلیدهای یک نسخه پیشوند دنباله‌ی دیگری است، نتیجه دقیقاً نسخه‌ی
   بلندتر است، بایت به بایت. (گفتگویی که فقط روی یک سیستم ادامه پیدا کرده.)
2. وگرنه یک گراف ترتیب ساخته می‌شود: گره = کلید یکتا؛ یال از هر خط به خط بعدی‌اش **در هر نسخه**، به‌علاوه‌ی یال
   `parentUuid → uuid` و `logicalParentUuid → uuid` وقتی هر دو سر در گراف هستند.
3. **مرتب‌سازی توپولوژیک** (Kahn). بین گره‌های آماده، انتخاب به این ترتیب:
   1. گره‌ای که در یکی از نسخه‌ها **بلافاصله بعد از آخرین گره‌ی انتخاب‌شده** آمده (تا هر شاخه پیوسته بماند و
      خطوط بی‌`uuid` کنار پیام‌های خودشان بمانند)؛
   2. بعد کوچک‌ترین «زمان مرتب‌سازی»: `timestamp` ی خود خط، یا اگر ندارد، `timestamp` ی نزدیک‌ترین خط قبلی همان
      نسخه که دارد؛
   3. بعد کوچک‌ترین کلید (مقایسه‌ی رشته‌ای).
4. اگر دور (cycle) پیش آمد (دو نسخه دو خط را برعکس هم مرتب کرده‌اند؛ نباید پیش بیاید)، از بین گره‌های باقی‌مانده
   کوچک‌ترین با همان معیار ۳-۲ و ۳-۳ برداشته می‌شود و ادامه. هیچ گرهی جا نمی‌ماند.
5. خروجی = خطوط به همان ترتیب، هر کدام دقیقاً با بایت‌های اصلی‌اش و `\n`.

ویژگی‌هایی که تست‌ها باید ثابت کنند: هیچ کلیدی از ورودی‌ها گم نمی‌شود؛ هیچ کلیدی دو بار نمی‌آید؛ ترتیب هر
نسخه‌ی ورودی حفظ می‌شود؛ نتیجه به ترتیب دادن ورودی‌ها بستگی ندارد (`merge(A,B) == merge(B,A)`)؛ و ادغام
دوباره‌ی نتیجه با هر کدام از ورودی‌ها همان نتیجه را می‌دهد (`merge(merge(A,B),B) == merge(A,B)`). تست
خاصیت‌محور (property-based) با جابه‌جایی تصادفی ترتیب ادغام سه نسخه هم لازم است.

#### مثال ۱: فقط یک طرف ادامه داده

```text
work:  u1 u2 u3 [last-prompt]                   (۴ خط)
home:  u1 u2 u3 [last-prompt] u4 u5 [last-prompt]  (۷ خط)
```

دنباله‌ی work پیشوند home است ← نتیجه = فایل home، بایت به بایت. روی work، اگر گفتگو باز نیست، فایل جایگزین
می‌شود. (اگر فایل محلی دقیقاً پیشوند نتیجه است، نوشتن می‌تواند به‌صورت **افزودن به انتها** باشد، نه
جایگزینی؛ بخش ۹-۲.)

#### مثال ۲: گفتگو روی هر دو سیستم ادامه پیدا کرده (PRD ۱۵-۱)

```text
مشترک:        u1 → u2 → u3
work ادامه:   a1 (parent u3, 10:00) → a2 (10:01) → [last-prompt leaf=a2]
home ادامه:   b1 (parent u3, 10:05) → b2 (10:06) → [last-prompt leaf=b2]
```

گراف: `u1→u2→u3→a1→a2→lpA` و `u3→b1→b2→lpB`. بعد از `u3` هر دو `a1` و `b1` آماده‌اند و هر دو در نسخه‌ی خودشان
بلافاصله بعد از `u3` آمده‌اند، پس معیار ۱ تساوی است و معیار زمان `a1` (10:00) را انتخاب می‌کند. بعد `a2` و `lpA`
با معیار ۱ (پیوستگی) می‌آیند، و در آخر `b1`، `b2`، `lpB`:

```text
u1 u2 u3 a1 a2 [lp a2] b1 b2 [lp b2]
```

هر دو شاخه کامل در فایل هستند؛ چون Claude Code گفتگو را از زنجیره‌ی `parentUuid` می‌سازد، هر شاخه درست خوانده
می‌شود. هر دو سیستم دقیقاً همین را می‌سازند (قطعی)، پس دور بعد اثر انگشت‌ها یکی است و چیزی برای ادغام نمی‌ماند.
اینکه `claude --resume` کدام شاخه را ادامه می‌دهد، سؤال باز ۳ است.

#### مثال ۳: خط نیمه‌کاره

```text
روی دیسک:  u1\n u2\n {"type":"assistant","uuid":"u3",...   (بدون \n)
```

خط سوم در نرمال‌سازی کنار گذاشته می‌شود (بخش ۹-۱)؛ نسخه‌ی این دور `u1 u2` است. دور بعد که خط کامل شده، `u3` هم
می‌آید. روی سیستم مقصد هم فایلی که آخرش خط نیمه‌کاره دارد بازنویسی نمی‌شود (یعنی کسی دارد می‌نویسد).

#### مسیر پروژه در متن گفتگو

فقط مقدار فیلد سطح اول `"cwd"` در هر خط بازنویسی می‌شود، آن هم به‌صورت **جایگزینی متنی همان رشته‌ی JSON** (نه
خواندن و دوباره نوشتن JSON، که ترتیب کلیدها و بایت‌ها را عوض می‌کند) و فقط اگر با مسیر پروژه‌ی این سیستم یا
زیرپوشه‌اش شروع شود (کل پیشوند؛ `/a/app` با `/a/app/x` جور است، با `/a/app-old` نه). در داده‌ی ذخیره‌شده به‌جای
پیشوند، نشانگر `{{karvan:project}}` می‌آید. هیچ چیز دیگری در متن گفتگو (پیام‌ها، خروجی ابزارها) دست نمی‌خورد.

### ۸-۲. فایل گفتگو در اپلیکیشن (`desktop`)

- اگر یکی بر دیگری غالب است (۵-۲)، همان. این حالت معمول است و به ساعت بستگی ندارد.
- اگر همزمان عوض شده‌اند: `lastActivityAt` ی بزرگ‌تر برنده است؛ در تساوی، اثر انگشت کوچک‌تر. نسخه‌ی بازنده
  دور ریخته می‌شود (این فایل فقط فهرست است؛ محتوای گفتگو در متن گفتگوست که ادغام می‌شود) ولی در لاگ ثبت
  می‌شود.
- **نشانگر مسیر:** در فیلدهای مسیر شناخته‌شده‌ی این فایل، پیشوند کامل مسیر پروژه با `{{karvan:project}}`
  جایگزین می‌شود و روی سیستم مقصد با مسیر خودش. فیلدهای دیگر بدون تغییر منتقل می‌شوند. فهرست دقیق فیلدهای مسیر
  باید روی فایل واقعی تأیید شود (سؤال باز ۱). مثل ۸-۱، جایگزینی روی متن JSON انجام می‌شود تا بقیه‌ی فایل
  بایت‌به‌بایت بماند.
- فایلی که مسیرش زیر هیچ پروژه‌ی تعریف‌شده‌ای نیست، منتقل نمی‌شود. فایلی که روی سیستم مقصد پروژه‌اش تعریف نشده،
  منتقل می‌شود ولی نوشته نمی‌شود (`status` می‌گوید).
- قانون‌های نوشتن وقتی اپلیکیشن باز است: ۹-۴.

### ۸-۳. متن (`text`) و `binary`

با `L` و `R` همزمان (هیچ‌کدام غالب نیست):

1. پایه `B` را پیدا کن (۵-۲).
2. اگر `B` هست و هر سه متن‌اند (UTF-8 ی معتبر، بدون بایت صفر)، ادغام سه‌طرفه‌ی خط‌به‌خط (diff3). اگر بدون
   تداخل شد، نتیجه نوشته می‌شود؛ `history` هر دو والد را دارد.
3. وگرنه (بدون پایه، تداخل خط‌ها، یا `binary`): **هر دو نسخه می‌مانند.** نسخه‌ی اصلی = آن که `mtime` ی بزرگ‌تری
   دارد (در تساوی، اثر انگشت کوچک‌تر)؛ دیگری در `<name>.conflict-<machine>` کنار همان فایل نوشته می‌شود که
   `<machine>` سیستمی است که آن نسخه را ساخته (سیستمی که ورودی‌اش با آن اثر انگشت، `changedAt` ی کوچک‌تری دارد؛
   در تساوی، اسم کوچک‌تر). مثلاً `CLAUDE.md.conflict-home`. هر دو سیستم دقیقاً همین را می‌سازند، پس فایل تداخل هم
   یک مسیر معمولی با محتوای یکسان روی همه است. کاربر در `status` و (اگر در hook است) با یک خط باخبر می‌شود و بقیه‌ی
   فایل‌ها متوقف نمی‌شوند. کاربر هر وقت فایل تداخل را پاک کند، پاک شدنش هم مثل هر حذفی منتقل می‌شود.

مثال: `CLAUDE.md` با پایه `B = "a\nb\nc\n"`؛ work خط اول را `A` کرده، home خط آخر را `C`:

```text
B:    a b c      work: A b c      home: a b C      ← نتیجه: A b C
```

اگر هر دو خط دوم را متفاوت عوض کرده بودند (`X` و `Y`)، `CLAUDE.md` نسخه‌ی جدیدتر می‌ماند و
`CLAUDE.md.conflict-<سیستم دیگر>` نسخه‌ی دیگر.

### ۸-۴. حذف در برابر تغییر

سنگ قبر `T` (با `T.history[0] = h`) مثل یک نسخه در قانون غالب بودن شرکت می‌کند:

| وضعیت دیگری `R` | نتیجه |
| ---- | ---- |
| `R.hash == h` (بعد از آخرین چیزی که من دیدم عوض نشده) | حذف برنده است: فایل روی آن سیستم هم پاک می‌شود. |
| `h ∈ R.history` (R بعد از نسخه‌ای که من پاک کردم تغییر کرده) | **تغییر برنده است:** فایل روی سیستم من دوباره ساخته می‌شود و سنگ قبر من کنار می‌رود. |
| همزمان (هیچ‌کدام غالب نیست) | تغییر برنده است. |

- حذف فقط برای `text` و `binary` منتقل می‌شود. گفتگوها، فایل‌های اپلیکیشن و `immutable` هرگز حذف منتقل‌شده ندارند
  (۷، مرحله‌ی ۲).
- سنگ قبر ۹۰ روز در فهرست می‌ماند و بعد حذف می‌شود. سیستمی که بیش از ۹۰ روز خاموش بوده و فایل قدیمی را دارد،
  آن را برمی‌گرداند؛ این قابل قبول است (چیزی گم نمی‌شود).
- پوشه‌ها مسیر منطقی ندارند: پوشه‌ای که خالی شد، روی سیستم مقصد هم اگر خالی است پاک می‌شود.

### ۸-۵. وضعیت خود هر سیستم (`owned`)

- مسیرهای `machine:<name>/...` را فقط سیستم `<name>` در فهرست خودش می‌گذارد. ورودی‌ای با این پیشوند در فهرست
  سیستم دیگری **نادیده گرفته می‌شود** و گزارش می‌شود.
- هیچ‌وقت ادغام نمی‌شوند و روی دیسک سیستم‌های دیگر نوشته نمی‌شوند؛ فقط خوانده می‌شوند (مثلاً `restore` عکس فوری
  کار نیمه‌تمام را از آن‌جا می‌گیرد، PRD ۶-۵).

## ۹. فایل‌هایی که در حال نوشته شدن‌اند

### ۹-۱. خواندن امن

1. `stat` (حجم، زمان تغییر با دقت نانوثانیه، inode).
2. کل فایل را بخوان.
3. دوباره `stat`. اگر چیزی عوض شده، تا ۳ بار تکرار (با ۲۰۰ میلی‌ثانیه فاصله)؛ بعد این فایل به دور بعد می‌رود.
4. برای `transcript`: هر چیزی بعد از آخرین `\n` کنار گذاشته می‌شود (خط نیمه‌کاره)، و همچنین خطی که JSON ی
   معتبر نیست ولی **آخرین** خط است (احتمالاً هنوز در حال نوشتن)؛ خط نامعتبر وسط فایل نگه داشته می‌شود (۸-۱).

### ۹-۲. نوشتن اتمی

- نوشتن در `<dir>/.karvan-tmp-<random>` در **همان پوشه**، `fsync`، تنظیم مجوزها مثل فایل قبلی (یا `0600` برای
  فایل جدید زیر `~/.claude`)، بعد `rename` روی فایل اصلی، و `fsync` ی پوشه. فایل‌های موقت جامانده در شروع هر دور
  پاک می‌شوند.
- **درست قبل از `rename`** دوباره `stat` ی فایل اصلی: اگر از زمان خواندن عوض شده، نوشتن لغو و مسیر به دور بعد
  می‌رود.
- **افزودن به انتها برای گفتگو:** اگر فایل محلی دقیقاً پیشوند نتیجه است (میان‌بر ۸-۱، حالت معمول)، به‌جای
  جایگزینی، فقط خطوط تازه با `O_APPEND` در یک `write` اضافه می‌شوند. این اگر برنامه‌ی دیگری فایل را باز نگه داشته
  باشد هم چیزی را خراب نمی‌کند. شرط‌های ۹-۳ همچنان لازم‌اند.
- `mtime` ی فایل نوشته‌شده همان `mtime` ی نسخه‌ی برنده تنظیم می‌شود (تا بازه‌ی ۷ روزه و فهرست «اخیر» ی Claude
  Code معنی‌دار بمانند).

### ۹-۳. گفتگویی که الان باز است

- **ارسال:** اجرای زمان‌بند گفتگویی را که فایلش در ۱۵ دقیقه‌ی اخیر عوض شده نمی‌فرستد. hookها (`SessionEnd`) و
  اجرای موقع خاموش شدن همه را می‌فرستند. (فرستادن گفتگوی باز اشکالی ندارد چون خط نیمه‌کاره کنار می‌رود؛ این
  قانون فقط ارسال‌های بی‌فایده را کم می‌کند.)
- **دریافت:** فایل گفتگوی محلی که «باز» است بازنویسی نمی‌شود؛ ادغام می‌ماند برای دور بعد و در `pending.json`
  ثبت می‌شود. «باز» یعنی: در ۱۵ دقیقه‌ی اخیر عوض شده، یا آخرش خط نیمه‌کاره دارد، یا `session_id` ی hook ی
  `SessionStart` ی همین اجرا است (گفتگویی که دارد باز می‌شود)، یا (اگر قابل تشخیص باشد) یک پروسه‌ی `claude` با همین
  `session_id` در حال اجراست. (سؤال باز ۲.)
- فایل گفتگوی **جدید** (که روی این سیستم نیست) همیشه نوشته می‌شود.

### ۹-۴. اپلیکیشن دسکتاپ

- فایل `desktop` ی **جدید** هر وقت نوشته می‌شود (اپلیکیشن فقط موقع باز شدن می‌خواندش).
- فایلی که از قبل هست، **فقط وقتی اپلیکیشن بسته است** عوض می‌شود. اگر باز است و نسخه‌ی تازه‌تری رسیده، مسیر به
  `pending.json` می‌رود و پیام: «اپلیکیشن را با Ctrl+Q ببندید و دوباره باز کنید». در دور بعد (یا با
  `karvan sync` بعد از بستن) نوشته می‌شود.
- تشخیص باز بودن: بسته‌ی مخصوص سیستم‌عامل (لینوکس: گشتن `/proc/*/exe` و `cmdline` برای فایل اجرایی اپلیکیشن).
  اگر تشخیص ممکن نبود، «باز» فرض می‌شود (احتیاط).

### ۹-۵. فایل‌های مشترک دیگر

`CLAUDE.md`، حافظه و مهارت‌ها را Claude Code هم ممکن است بنویسد؛ همان خواندن امن (۹-۱) و نوشتن اتمی با بررسی
قبل از `rename` (۹-۲) کافی است.

### ۹-۶. یک اجرا در هر لحظه

- قفل فایل `~/.local/state/karvan/lock` با قفل سیستم‌عامل (`flock` از راه syscall روی لینوکس و مک،
  `LockFileEx` روی ویندوز؛ نه فرمان `flock`). قفل با مردن پروسه خودش آزاد می‌شود. PID و زمان شروع داخل فایل
  نوشته می‌شود فقط برای پیام.
- زمان‌بند: اگر قفل گرفته است، بی‌صدا خارج می‌شود. hook ی `SessionStart`: حداکثر ۱۰ ثانیه صبر، بعد بدون
  همگام‌سازی ادامه و یک خط پیام. `karvan sync` ی دستی: می‌گوید منتظر چیست و صبر می‌کند.
- هر دور یک مهلت کلی دارد (پیش‌فرض ۵ دقیقه) و هر عمل شبکه‌ای مهلت خودش را (PRD ۷).

## ۱۰. پاک‌سازی blobهای بی‌استفاده

- **چه چیزی زنده است:** هر تکه‌ای که در `chunks` ی یک ورودی فعلی هر فهرستی آمده، به‌علاوه‌ی تکه‌های نسخه‌هایی
  که در `history` هستند و هنوز در محل ذخیره‌اند (چون پایه‌ی ادغام سه‌طرفه‌اند). برای این دومی، فهرست هر سیستم
  برای مسیرهای `text` تکه‌های تا ۸ نسخه‌ی آخر تاریخچه را هم در فیلد `historyChunks` نگه می‌دارد.
- **چه کسی:** هر سیستم حداکثر روزی یک بار، فقط اگر همه‌ی فهرست‌ها را بدون خطا خوانده باشد.
- **دو مرحله با مهلت:** سیستم فهرست blobهای مرده را با زمان اولین دیدن در `gc/<machine>.krv` می‌نویسد. blob ی
  فقط وقتی پاک می‌شود که (۱) در دفترچه‌ی **همان سیستم** حداقل ۱۴ روز پیش مرده دیده شده، (۲) الان هم مرده است،
  و (۳) همه‌ی سیستم‌هایی که فهرست دارند در این ۱۴ روز حداقل یک بار فهرستشان را نوشته‌اند (پس فهرست قدیمی‌ای در
  راه نیست که به آن اشاره کند). سیستمی که بیش از ۱۴ روز خاموش بوده، پاک‌سازی همه را عقب می‌اندازد؛ `status`
  این را نشان می‌دهد.
- **ترمیم خودکار:** قبل از نوشتن فهرست (مرحله‌ی ۶)، وجود تکه‌هایی که فهرست به آن‌ها اشاره می‌کند ولی این دور
  فرستاده نشده‌اند بررسی می‌شود (`list` ی پوشه‌های مربوط)؛ اگر نبود و محتوا محلی هست، دوباره `put` می‌شود. پس
  حتی اگر پاک‌سازی همزمان با یک ارجاع تازه پیش برود، دور بعد درستش می‌کند.
- در git، پاک کردن blob فقط از commit ی آخر است؛ تاریخچه‌ی git همچنان آن را دارد (سؤال باز ۵).

## ۱۱. اختلاف ساعت

- هیچ تصمیم درستی‌ای به ساعت سیستم‌های مختلف وابسته نیست: غالب بودن از تاریخچه‌ی اثر انگشت‌ها می‌آید.
- ساعت فقط در این‌ها اثر دارد:
  - ترتیب خطوط دو شاخه‌ی همزمان در گفتگو (فقط ترتیب، هیچ خطی گم نمی‌شود)؛
  - برنده‌ی `desktop` وقتی هر دو همزمان عوض شده‌اند؛
  - انتخاب نسخه‌ی اصلی در تداخل متن (هر دو نسخه می‌مانند)؛
  - قانون‌های محلی (۱۵ دقیقه، ۷ روز، ۱۴ روز پاک‌سازی، ۹۰ روز سنگ قبر) که همه با ساعت **خود همان سیستم**
    سنجیده می‌شوند، روی زمان‌هایی که خود همان سیستم ثبت کرده.
- **تشخیص:** اگر `writtenAt` ی فهرست سیستم دیگری بیش از ۵ دقیقه در آینده‌ی ساعت این سیستم باشد، یا (در git) زمان
  commit ی تازه از سرور بیش از ۵ دقیقه با ساعت محلی فرق کند، `status` و `doctor` هشدار می‌دهند («ساعت این سیستم
  یا work تنظیم نیست؛ NTP را روشن کنید»). همگام‌سازی متوقف نمی‌شود.

## ۱۲. نسخه‌ی قالب‌ها و قالب ناشناخته

### ۱۲-۱. قالب محل ذخیره

`FORMAT` (JSON ی بدون رمز):

```json
{ "format": 1, "minReader": 1, "created": "2026-11-16T17:00:00Z", "createdBy": "karvan 0.1.0",
  "hash": "sha256", "chunking": "lines-v1", "encryption": "none" }
```

- Karvan هر قالبی را که `format` اش ≤ بیشترین قالبی است که می‌شناسد، می‌خواند.
- اگر `minReader` بزرگ‌تر از قالبی است که این نسخه می‌شناسد: **هیچ چیز نمی‌خواند و نمی‌نویسد**؛ پیام «Karvan را
  به‌روز کنید». این برای همه‌ی بخش‌ها توقف است، چون معنی blobها را نمی‌داند.
- اگر `format` بزرگ‌تر است ولی `minReader` قابل خواندن است (افزودنی‌های سازگار): می‌خواند و می‌نویسد، فیلدهای
  ناشناخته را نادیده می‌گیرد.
- ارتقای قالب فقط با فرمان صریح (`karvan migrate`) و بعد از اینکه همه‌ی سیستم‌ها نسخه‌ی جدید را دارند (از روی
  فیلد `karvan` در فهرست‌ها) انجام می‌شود. M0 → M1 (قالب ۲، رمزنگاری) یک محل ذخیره‌ی **تازه** می‌سازد و همه‌چیز
  را از دیسک دوباره می‌فرستد؛ محل ذخیره‌ی M0 فقط برای تست است.

### ۱۲-۲. قالب فهرست

- `format` ی هر فهرست همان قالب محل ذخیره است. فیلدهای ناشناخته نادیده گرفته می‌شوند.
- ورودی با `kind` ی ناشناخته: آن مسیر نه نوشته می‌شود، نه پاک؛ گزارش می‌شود.
- فهرست خراب (پوشش یا JSON ی نامعتبر): آن سیستم این دور نادیده گرفته می‌شود و گزارش می‌شود؛ هیچ‌وقت به معنی «همه
  را پاک کرده» تعبیر نمی‌شود.

### ۱۲-۳. ساختار داده‌های Claude (PRD ۱۲)

- **متن گفتگو:** Karvan فقط به `type`، `uuid`، `parentUuid`، `logicalParentUuid`، `timestamp`، `cwd` و
  `version` تکیه می‌کند. قالب `cc-jsonl` یعنی: هر خط کامل JSON است، و خطوط `user`/`assistant` همه `uuid`
  دارند. اگر در یک فایل بیش از ۵٪ خطوط کامل JSON ی نامعتبر باشند، یا خطوط `user`/`assistant` بی‌`uuid` باشند،
  قالب ناشناخته است: همگام‌سازی **متن گفتگوها** متوقف می‌شود (فایل‌ها دست نمی‌خورند)، بقیه ادامه می‌دهد و به کاربر
  گفته می‌شود. فیلد `version` ی خطوط در لاگ و `doctor` نشان داده می‌شود.
- **فایل‌های اپلیکیشن:** باید `lastActivityAt` و فیلدهای مسیر شناخته‌شده را داشته باشند؛ وگرنه همگام‌سازی
  `desktop` متوقف می‌شود. فیلدهای دیگر بدون تغییر منتقل می‌شوند.
- برای هر دو، تست‌ها روی نمونه‌های واقعی (ناشناس‌شده) از نسخه‌های فعلی اجرا می‌شوند؛ اضافه کردن قالب جدید یعنی
  اضافه کردن یک تابع تشخیص و یک نمونه‌ی تست (هدف PRD: اصلاح ظرف یک ساعت).

## ۱۳. محل‌های ذخیره

رابط Go (در فاز ۳ دقیق می‌شود):

```go
type Store interface {
    Get(ctx context.Context, path string) ([]byte, error)          // ErrNotFound
    Put(ctx context.Context, path string, data []byte) error        // only for content-addressed blobs
    List(ctx context.Context, prefix string) ([]string, error)
    // Commit atomically publishes the staged blobs and this machine's manifest,
    // if the store has not changed since the snapshot the caller read.
    // ErrConflict means: read again, decide again, retry.
    Commit(ctx context.Context, snap Snapshot, manifest []byte, gcDeletes []string) error
}
```

`Snapshot` همان چیزی است که مرحله‌ی ۳ خوانده (git: commit ی سر شاخه؛ پوشه: `seq` ی فهرست خودم).

### ۱۳-۱. git (با go-git)

| عمل | پیاده‌سازی |
| ---- | ---- |
| خواندن وضعیت | `ls-remote` برای سر شاخه، بعد fetch ی فقط همان شاخه (depth 1)، بعد تنظیم ref ی ردیابی **توسط خود Karvan** و بررسی اینکه سر قبلی جد سر جدید است |
| `list` / `get` | خواندن از tree ی همان commit در مخزن bare ی محلی (`~/.cache/karvan/store.git`)؛ بدون worktree و checkout |
| `put` | ساختن blob ی git در مخزن محلی و اضافه کردنش به tree ی commit ی در حال ساخت |
| نوشتن شرطی | ساختن **یک** commit با والد = سر شاخه‌ی خوانده‌شده و tree = همان tree + blobهای تازه + فهرست من (− حذف‌های پاک‌سازی)؛ push ی بدون `+` با `RequireRemoteRefs` (سر شاخه باید هنوز همان باشد) |
| رد شدن | fetch، مرحله‌های ۳ تا ۷ ی چرخه، ساختن commit **از نو** روی سر جدید (نه rebase، نه merge)، push. حداکثر ۵ بار |
| هرگز | force push، merge commit، rebase، تغییر شاخه‌ای غیر از شاخه‌ی Karvan |

- شاخه: `main` (قابل تنظیم). نویسنده‌ی commit: `Karvan (<machine>) <karvan@invalid>`؛ هیچ اطلاعات شخصی‌ای نه.
  پیام commit: `sync <machine> seq <n>`.
- `pack.window = 0` (بدون جست‌وجوی delta؛ blobها فشرده‌اند). commitها حداکثر ~۳۲ مگابایت داده‌ی تازه دارند.
- **عقب رفتن شاخه** (کسی با force push تاریخچه را عوض کرده): همگام‌سازی متوقف و به کاربر گفته می‌شود. Karvan آن را
  «درست» نمی‌کند. همچنین اگر `seq` ی فهرست خودم در محل ذخیره کمتر از `publishedSeq` ی وضعیت محلی باشد (محل ذخیره
  از نسخه‌ی پشتیبان برگشته)، همین رفتار.
- **کلید میزبان SSH:** فقط از `known_hosts` ی کاربر (و `/etc/ssh/ssh_known_hosts`)؛ هرگز پذیرفتن خودکار کلید
  ناشناخته. Karvan خودش پایگاه `known_hosts` را باز می‌کند و نوع‌های کلید ثبت‌شده برای `host:port` را به‌عنوان
  `HostKeyAlgorithms` تنظیم می‌کند، چون go-git v5.19.3 این کار را نمی‌کند و بدون آن `key mismatch` می‌دهد (یافته‌ی ۶
  آزمایش). `doctor` نبودن کلید برای `[ssh.github.com]:443` را تشخیص می‌دهد و فرمان `ssh -T -p 443 git@ssh.github.com`
  را پیشنهاد می‌کند.
- یافته‌های آزمایش go-git (`spikes/gogit/README.md`) در همین جدول لحاظ شده‌اند: fetch ی go-git به عقب رفتن شاخه
  اعتنا نمی‌کند (برای همین `ls-remote` و بررسی جد)، رد شدن همزمان گاهی به شکل `failed to update ref` می‌آید و آن هم
  «رد شدن» است، و شاخه‌ی محلی هرگز روی commit ی push‌نشده نمی‌ماند.

### ۱۳-۲. بررسی هویت فهرست خودم (همه‌ی محل‌ها)

در مرحله‌ی ۳: اگر `manifests/<machine>.krv` در محل ذخیره هست و (الف) `machineId` اش با این سیستم فرق دارد یا (ب)
`seq` اش از `publishedSeq` ی محلی **بیشتر** است، یعنی سیستم دیگری با همین اسم می‌نویسد (مثلاً دیسک کپی شده): توقف
و پیام. اگر **کمتر** است: محل ذخیره عقب رفته (۱۳-۱). در هیچ‌کدام چیزی نوشته نمی‌شود.

### ۱۳-۳. پوشه‌ی محلی یا ابری

- `put`: نوشتن در `blobs/<hh>/.tmp-<random>` و `rename`. اگر blob هست، دوباره نوشته نمی‌شود.
- نوشتن شرطی فهرست: خواندن دوباره‌ی فهرست خودم و بررسی `seq` و `machineId` (۱۳-۲)، بعد نوشتن در فایل موقت و
  `rename`. چون فقط همین سیستم این فایل را می‌نویسد، این «شرط» فقط جلوی دو سیستم هم‌نام و برگشت از پشتیبان را
  می‌گیرد؛ نوشتن فهرست سیستم‌های دیگر هیچ‌وقت تداخل نیست و تکرار لازم ندارد.
- پوشه‌ی ابری ترتیب رسیدن فایل‌ها را تضمین نمی‌کند: فهرستی ممکن است زودتر از blobهایش برسد. خواندن blob ی
  ناموجود یا خراب آن مسیر را به دور بعد می‌برد (۳-۳). فایل‌های تداخلی که خود سرویس ابری می‌سازد نادیده گرفته
  می‌شوند (۲).

## ۱۵. سؤال‌های باز (برای نگهدارنده)

1. **فیلدهای مسیر در فایل‌های اپلیکیشن.** در این محیط اپلیکیشن دسکتاپ نیست و دسترسی خواندن به `sessions.sh` ی
   نمونه رد شد، پس نمی‌دانم دقیقاً کدام فیلدهای `local_<id>.json` مسیر دارند (`cwd`؟ مسیر worktree؟) و آیا
   `<account>/<org>` روی دو سیستم یکی است. پیشنهاد: در فاز ۷ از روی یک فایل واقعی (یا خود `sessions.sh`) فهرست
   شود. می‌توانید `sessions.sh` را این‌جا بدهید یا اجازه‌ی خواندنش را بدهید؟
2. **تشخیص «گفتگوی باز».** آیا Claude Code فایل گفتگو را باز نگه می‌دارد یا برای هر خط از نو باز می‌کند؟ و آیا
   پروسه‌ی `claude` شناسه‌ی گفتگو را در `cmdline` دارد؟ تا روشن شدن، قانون ۱۵ دقیقه + خط نیمه‌کاره + hook است.
3. **وقتی گفتگو دو شاخه دارد، `claude --resume` کدام را ادامه می‌دهد؟** (احتمالاً شاخه‌ی آخر فایل یا
   `leafUuid` ی آخرین `last-prompt`.) اگر لازم باشد، الگوریتم ۸-۱ می‌تواند شاخه‌ای را که آخرین پیام جدیدتری دارد
   آخر بگذارد. شما کدام را می‌خواهید: شاخه‌ی جدیدتر، یا شاخه‌ی همین سیستم؟
4. **زمان hook ی `SessionStart`:** آیا قبل از خواندن متن گفتگو برای `--resume` اجرا می‌شود؟ اگر بعدش است، ادغام
   برای همان گفتگو یک دور دیر می‌رسد (و Claude یک شاخه‌ی تازه می‌سازد، بدون گم شدن چیزی). شاید راهنمای کاربر
   باید بگوید «قبل از resume روی سیستم دوم یک `karvan sync` بزنید» یا hook ی `startup` کافی است.
5. **رشد repo ی git.** پاک‌سازی blobها از commit ی آخر، حجم تاریخچه‌ی git را کم نمی‌کند. با تکه‌ها، هر دور فقط
   تکه‌های آخر فرستاده می‌شود (برآورد: چند ده کیلوبایت فشرده در هر دور برای هر گفتگوی فعال)، ولی در ماه‌ها جمع
   می‌شود. پیشنهاد برای بعد از M0: «دوره»‌ها: یک شاخه‌ی تازه‌ی بدون تاریخچه (`karvan-epoch-N`) که سیستم‌ها با
   اشاره‌ای در `FORMAT` به آن می‌روند و شاخه‌ی قدیمی را کاربر آگاهانه پاک می‌کند. این برای M0 لازم است یا بعداً؟
6. **حذف گفتگو در اپلیکیشن.** اگر کاربر گفتگویی را از فهرست اپلیکیشن پاک کند، این مشخصات آن را منتقل نمی‌کند
   (`retired`، نه حذف). درست است، یا باید حذف از فهرست اپلیکیشن هم به سیستم‌های دیگر برود؟
7. **مسیرها داخل پیام‌های گفتگو.** فقط `cwd` بازنویسی می‌شود؛ مسیرهای داخل متن پیام‌ها و خروجی ابزارها مسیر سیستم
   مبدأ می‌مانند (Claude معمولاً با آن کنار می‌آید). نمونه‌ی bash چه می‌کرد؟
8. **پوشه‌ی `tool-results` و subagentها:** نمونه‌ی bash احتمالاً فقط `<session>.jsonl` را منتقل می‌کرد. منتقل
   کردن این‌ها (که خروجی‌های بزرگ ابزار را دارند) حجم را بالا می‌برد ولی بدونشان بعضی ارجاع‌های گفتگو روی سیستم
   دیگر خالی است. پیش‌فرض این سند: منتقل شوند. موافقید؟
9. ~~نتیجه‌ی آزمایش SSH روی پورت ۴۴۳~~ **پاسخ داده شد:** روی سیستم نگهدارنده همه‌ی مراحل پاس شد، از جمله رد شدن و
   تلاش دوباره، بدون force push (`spikes/gogit/README.md`). در همین اجرا باگ کلید میزبان go-git پیدا و دور زده شد
   (۱۳-۱).
10. **تأخیر hook ی `SessionStart`.** روی شبکه‌ی نگهدارنده هر اتصال SSH ۱ تا ۲ ثانیه است و یک دور کامل ۵ تا ۸ ثانیه
    شبکه می‌خواهد. پیشنهاد: `SessionStart` فقط با مهلت کوتاه (مثلاً ۸ ثانیه) می‌گیرد و می‌نویسد و بقیه را به یک
    اجرای پس‌زمینه می‌سپارد؛ و `Fetch` اگر سر شاخه از `ls-remote` عوض نشده، fetch نمی‌زند (همین الان این‌طور است).
    بعداً می‌شود یک اتصال SSH را برای هر دو کار نگه داشت. قبول است؟
11. **اسم پوشه‌ی پروژه برای مسیرهای خیلی بلند.** قاعده‌ی پیاده‌شده در `internal/paths` (فاز ۱): هر نویسه‌ای جز حرف و
    رقم ASCII به `-` تبدیل می‌شود (مثل `-home-user-Karvan` که در این محیط دیده شد؛ نویسه‌ی بیرون از BMP، مثل
    ایموجی، `--` می‌شود چون Claude Code با JavaScript و UTF-16 کار می‌کند). تأیید نشده که Claude Code اسم‌های خیلی
    بلند (مثلاً بیش از ۲۰۰ نویسه) را کوتاه می‌کند یا نه. `karvan doctor` برای هر پروژه بررسی می‌کند که پوشه‌ی
    محاسبه‌شده واقعاً هست و اگر نبود هشدار می‌دهد.
